## Phase 1 — Initial Flash & Boot

### Flashed firmware

```
rt-esp32 (vehicle env) → COM6 (RT board)
sys-esp32 (vehicle env) → COM5 (SYS board)
```

Build: `platform = espressif32@6.12.0`, `framework = espidf@5.5.0`.

### RT boot result: ❌ Crash loop

```
task_wdt: CPU 0: rx_high
Mcp2515Driver::receive() → spi_read_byte() → spi_device_transmit()  [stuck]
```

**Finding:** `rx_high` task hung in MCP2515 SPI polling. `spi_device_transmit()` blocked forever,
starving IDLE0 and triggering task watchdog every 5 seconds. TWAI status unknown — MCP2515
dominated the watchdog output.

### SYS boot result: ❌ Crash loop

```
gpio_set_direction(308): GPIO number error
gpio_set_level(238): GPIO output gpio_num error
vApplicationStackOverflowHook → abort() → reboot
```

Reset count: 559 → 1600+ in ~15 seconds. Stack overflow detected during task switch.

**Finding:** SYS crashed immediately after CAN init. GPIO values 308 and 238 are invalid for
ESP32-S3 (max GPIO = 48). These were symptoms of stack corruption, not literal config values
(no reference to 308 or 238 exists in source code).

## Phase 2 — Root Cause Analysis

### RT MCP2515 isolation test

Temporarily forced `has_high_can = false` to skip MCP2515 init and observe TWAI in isolation.

**Result:** New crash — `assert failed: xTaskDelayUntil (xTimeIncrement > 0U)` in `t_can_tx_low`
at `main.cpp:452`. Function calls `vTaskDelayUntil(&last_wake, pdMS_TO_TICKS(5))`.

### Root cause: CONFIG_FREERTOS_HZ = 100 (not 1000)

ESP-IDF Kconfig defaults to `CONFIG_FREERTOS_HZ=100` (10ms tick). The build flag
`-D CONFIG_FREERTOS_HZ=1000` was overridden by sdkconfig.h's unconditional `#define`.

With 100 Hz tick:
- `pdMS_TO_TICKS(5) = (5 * 100) / 1000 = 0` → triggers FreeRTOS assert
- `pdMS_TO_TICKS(1) = (1 * 100) / 1000 = 0` → `ulTaskNotifyTake(pdTRUE, 0)` returns immediately
- MCP2515 receive loop polls SPI at full speed with zero delay → SPI bus lockup

All `pdMS_TO_TICKS()` calls with values under 10ms evaluated to zero.

### Fix

Created `shared/can/patch_sdkconfig.py` — a PlatformIO pre-build script that patches the
generated `sdkconfig.h` after CMake configure, rewriting `CONFIG_FREERTOS_HZ` from 100 to 1000.

Also attempted `sdkconfig.defaults` and `board_build.esp_idf.sdkconfig_append` — neither was
picked up by PlatformIO's CMake wrapper. The pre-build script approach works reliably.

## Phase 4 — SYS Fix

### Changes

| File | Change |
|------|--------|
| `sys-esp32/sdkconfig.defaults` | Created (documentation reference) |
| `sys-esp32/platformio.ini` | Added `patch_sdkconfig.py` to `extra_scripts` |
| `sys-esp32/src/main.cpp` | Increased all task stack sizes (min 1536→2048, others +512) |

### Initial attempt: Still crashing

After HZ fix, GPIO errors (308, 238) disappeared — confirmed they were stack corruption
from incorrect tick timing. But SYS still crashed with `vApplicationStackOverflowHook`
after "Queues created".

### Final fix: Increased task stacks

With 1000 Hz tick (1ms vs 10ms), FreeRTOS context switching uses more CPU and stack.
The minimum task stack was 1536 bytes — too tight for 1ms tick ISR overhead. Increased:
- `gear`: 1536→2048
- `lights`, `dcdc`, `indicator`, `power`, `hb`: 2048→2560
- `can_rx`, `safety`: 4096→4608
- `dispatch`, `brake`, `can_tx`, `diag`: 3072→3584
- `mode`: 2048→2560
- `CONFIG_ESP_MAIN_TASK_STACK_SIZE`: 3584→6144 (via patch script)

### Result: ✅ SYS boots and runs (after full flash erase)

Full chip erase was needed to clear NVS corruption from 6600+ crash-loop reboots.

```
I (284) can: TWAI TX=5 RX=4 @ 500 kbit/s   ← TWAI init OK
I (292) sys: Queues created                  ← Tasks created OK
```

SYS now runs stably. CAN TX errors are expected on bench (no other nodes to ACK frames
to 0x7B9 brake, 0x001 ESTOP, etc.). These are protocol-level — the hardware works.

**Remaining known issue:** GPIO 238 errors appear at runtime (~50ms intervals).
Value 238 = 0xEE is an uninitialized-memory pattern. Non-fatal, affects a peripheral
task output pin. To be investigated separately.

## Phase 5 — CAN Bus Verification

### Test setup

Created `can-test/` — a minimal PlatformIO project with no RTOS tasks, just a bare
`app_main` loop using ESP-IDF TWAI driver directly.

- TWAI: TX=GPIO5, RX=GPIO4, 500 kbit/s, 8MHz timing resolution
- Each board sends a test frame (CAN ID 0x555, 4-byte counter) every 500ms
- Receives and prints any incoming frames
- Reports error counters every 5 seconds

### Test code

`can-test/src/main.cpp` — single-file test, ~150 lines. Initializes TWAI driver,
polls for RX in a loop, transmits every 500ms.

### Results: ✅ CAN bus fully operational

**COM6 (RT board) — perfect link:**
```
TEC=0  REC=0  tx_fail=0  rx_miss=0  bus_err=0
rx=126  tx=118  fail=0
```

**COM5 (SYS board) — good link, stale error counters from pre-connection:**
```
TEC=7↓ REC=0  tx_fail=0 (after initial 2)
rx=669  tx=106  fail=2 (initial only)
```

Bidirectional traffic confirmed:
```
COM5:  RX id=0x555 data=00 00 00 09    ← from COM6
       TX id=0x555 data=00 00 00 22    → to COM6
COM6:  TX id=0x555 data=00 00 00 2D    → to COM5
       RX id=0x555 data=00 00 00 46    ← from COM5
```

Both boards receive each other's frames. Every transmission is ACKed at the CAN
controller level. Zero bus errors on the clean link.

## Phase 6 — MCP2515 SPI Verification

### Test setup

`can-test/src/spi_test.cpp` — dedicated MCP2515 SPI test using the same pins as
rt-esp32 production firmware:

| Signal | GPIO | ESP32-S3 Function |
|--------|------|-------------------|
| SCK | 36 | SPI2 (FSPI) clock |
| MOSI | 37 | SPI2 MOSI |
| MISO | 38 | SPI2 MISO |
| CS | 39 | SPI2 chip select |
| INT | 40 | MCP2515 interrupt (not used in test) |

Test sequence:
1. Initialize SPI bus at 8 MHz, mode 0
2. Send MCP2515 RESET command (0xC0)
3. Read CANSTAT register (0x0E) — the definitive presence check
4. Dump all key registers (CANCTRL, CANINTE, CANINTF, EFLG, TEC, REC, CNF1-3, RXBCTRL)
5. READ STATUS command test
6. Bit-modify test (read-modify-write on RXB0CTRL)
7. Continuous monitoring loop (reads CANSTAT every 5 seconds)

### Results: ✅ MCP2515 present and responding

```
CANSTAT = 0x80  (OPMODE=Configuration, ICODE=No-Interrupt)
MCP2515: PRESENT & RESPONDING
```

Test ran for 27+ consecutive 5-second loops (~2.5 minutes) with zero errors. Every
SPI read returned the expected `CANSTAT=0x80` (Configuration mode — chip was reset
but not configured, which is the correct post-reset state).

**Interpretation of CANSTAT=0x80:**
- Bit 7-5 = 0b100 = 4 = Configuration mode (correct after reset)
- Bit 4-3 = 0b00 = reserved
- Bit 2-1 = 0b00 = No interrupt pending (normal)
- Bit 0 = 0 = reserved

The MCP2515 chip is physically populated, wired correctly on the SPI bus, and
responding to all SPI commands (read, write, reset, bit-modify, read-status).

The earlier SPI hang (Phase 1) was entirely caused by the 100 Hz tick rate producing
a zero-delay polling loop that overwhelmed the SPI bus or the MCP2515. With the
1000 Hz tick, `ulTaskNotifyTake(pdTRUE, pdMS_TO_TICKS(1))` correctly waits 1ms
for the INT pin notification before polling, reducing SPI traffic by orders of
magnitude.

## Key Technical Findings

### 1. ESP-IDF Kconfig overrides build flags

`-D CONFIG_FREERTOS_HZ=1000` in `build_flags` is silently overridden by sdkconfig.h's
unconditional `#define CONFIG_FREERTOS_HZ 100`. The only reliable fix is to patch
sdkconfig.h after CMake configure via a pre-build script. `sdkconfig.defaults` is
not reliably picked up by PlatformIO's CMake wrapper.

### 2. 1000 Hz tick requires larger task stacks

The default ESP-IDF main task stack (3584 bytes) and small task stacks (1536 bytes)
are borderline at 1000 Hz. The faster tick rate means:
- ISR prologue/epilogue runs 10× more frequently
- Task switches happen 10× more often
- Stack canary check runs 10× more often
- `pdMS_TO_TICKS()` values increase 10× (but FreeRTOS tick lists remain O(1))

### 3. CAN bus ACK requirement

Standalone CAN TX always fails because CAN requires at least one other node to
acknowledge each frame at the controller level. This is normal — the CAN controller's
TEC (Transmit Error Counter) will climb until another node joins the bus.

### 4. Windows COM port assignment

Windows assigns COM numbers dynamically per USB port + device serial. Same board on
same USB port can get different COM numbers across unplugs. Use MAC address or
`pio device list` to identify boards, not COM numbers.
