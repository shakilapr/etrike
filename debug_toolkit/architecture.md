# Debug Toolkit (Python) Architecture

> **Version:** v1.0.0-draft — Lightweight, single-process CAN bench-test platform
> **Target:** Replace the legacy Node/Svelte `debug-tool` with a monolithic CustomTkinter Python app.

This document outlines the architecture for the `debug_toolkit`—a browserless, single-process, highly optimized desktop application. It eliminates over 13,000 Source Lines of Code (SLOC) by removing web servers (Fastify), databases (SQLite), message brokers (Aedes MQTT), and JavaScript UI frameworks (Svelte), returning to a clean, direct hardware-to-UI paradigm.

---

## 1. Topology

```
                          ┌───────────────────────────┐
                          │   CustomTkinter GUI       │
                          │   (Main Thread)           │
                          │   - Dashboard, Monitor,   │
                          │   - Controller, Stats     │
                          └──────┬────────────▲───────┘
                                 │ Commands   │ (Polled Queue)
                          ┌──────▼────────────┴───────┐
                          │    Transport Manager      │
                          │    (Thread)               │
                          └────┬─────────────────┬────┘
                               │                 │
                   ┌───────────▼─────────┐   ┌───▼───┐
                   │  Simulation Engine  │   │ HW I/O│
                   │  (100 Hz Thread)    │   └───────┘
                   │  - MtrModel         │      │
                   │  - RtModel          │   Serial /
                   │  - SesModel         │  CANalyst-II
                   └─────────────────────┘
```

The application runs in a single Python process:
1. **GUI Thread (Main):** Runs the CustomTkinter `.mainloop()`. It periodically polls a thread-safe `queue.Queue` to ingest incoming decoded frames and updates the UI (TreeViews, Labels, Charts) synchronously, ensuring the event loop is never blocked by I/O.
2. **Transport Thread:** Manages the active bridge (Serial, CANalyst-II, or Simulator). It blocks on I/O reads (e.g., `pyserial.readline()` or pyusb bulk reads), decodes frames immediately, and pushes them to the GUI queue.
3. **Simulation Thread (Optional):** When in "full-sim" or "emulator" mode, a 100 Hz loop calculates vehicle physics and ECU state machines, injecting synthetic frames into the virtual bus.

## 2. CAN Message Catalog (Zero Code Generation)

The legacy tool suffered from duplicated, hand-coded TypeScript decoders that diverged from the firmware's DBC/YAML sources. The `debug_toolkit` eliminates this technical debt entirely.

On startup, `decoder.py` reads `shared/can/can_high.yaml` and `shared/can/can_low.yaml` using `pyyaml`. It builds a dynamic lookup dictionary of all messages and signals.

A single, unified Python function processes **all** encoding and decoding operations using dynamic bitwise shifting:
- Handles **Intel (Little-Endian)** (e.g., `VCU_SES_REQ`).
- Handles **Motorola (Big-Endian)** (e.g., `SYS_THROTTLE_STS`).
- Applies bitwise clipping, signed 2's complement extraction, offsets, and scale factors.

Changes to the CAN database YAML files instantly reflect in the GUI upon restart—**no compilation or code generation required.**

## 3. Transport Modes

The transport layer abstracts hardware communication into a simple `Bridge` interface.

### 3.1 Serial (ESP32)
Uses `pyserial` to connect to the ESP32-S3 USB CDC ACM port. Reads JSON Lines generated by the firmware (`{"id":"0x204","data":[0,0,7,208,1]}`).
- **Auto-reconnect:** Backoff strategy handled internally.

### 3.2 CANalyst-II
Direct integration using the `canalystii` Python package and `pyusb` (WinUSB).
- Eliminates the legacy architecture's need to spawn a python sub-process from Node.js and pipe stdin/stdout.
- Configurable baud rates and channel mappings.

### 3.3 Simulator
A virtual bridge that connects exclusively to the internal Simulation Engine.

## 4. Simulation Engine & ECU Mimicking

The toolkit retains the powerful bench-testing orchestrator of the legacy tool. `sim_engine.py` operates a 100 Hz clock tick.

Supported models:
- **RtModel**: Processes `0x300` HOST drive commands, manages the ESTOP state machine, and translates output to the low bus.
- **MtrModel**: Simulates motor inertia and rate limiting. Calculates actual speed and outputs `0x120` and `0x206`.
- **SesModel & SebModel**: Implements first-order tracking equations for steering angle and brake pressure, generating status and diagnostic reports (`0x201`, `0x202`, etc.).

### Work Modes
- **full-sim**: All ECUs are mimicked. Perfect for UI/Host development.
- **emulator**: Mimics only missing hardware ECUs to complete a bench setup.
- **bench**: Pure hardware testing, optionally applying bypasses (e.g., `sesSync`) to disable initialization routines.

## 5. User Interface (CustomTkinter)

The UI leverages hardware-accelerated Tkinter via CustomTkinter to deliver a modern, dark-themed experience.

- **Monitor Tab:** A highly optimized `CTkScrollableFrame` or `Treeview` that buffers incoming frames. To prevent rendering lag at 2000+ FPS, the view is decoupled from the raw data stream; it renders only the "latest frame per ID" or chunks updates.
- **Injector Tab:** Auto-generates entry fields (with min/max/unit hints) based on the YAML schema for any selected CAN ID. Supports periodic and one-shot injection.
- **Controller Tab:** Standard WASD key bindings using `<KeyPress>` and `<KeyRelease>` events to allow seamless desktop driving of the simulator.

## 6. Architectural Advantages

| Metric | Legacy `debug-tool` | `debug_toolkit` (Python) | Improvement |
|--------|---------------------|--------------------------|-------------|
| **SLOC** | ~13,600 | < 1,000 | **>90% reduction** |
| **Processes** | 3 (Node, Vite, Python) | 1 (Python) | Unified runtime |
| **Dependencies** | 1000+ (`node_modules`) | 4 (`pip install`) | Zero-friction setup |
| **Databases** | SQLite (Synchronous I/O) | In-Memory (Deque/Queue) | Zero DB locking |
| **CAN Sync** | Manual TS duplication | Direct YAML parsing | Perfect sync |

## 7. Missing Capabilities & Trade-offs (Compared to Legacy Tool)

A deep review of the legacy `debug-tool` architecture and testing plans (`testing-plan.md`, `debug-tool-architecture.md`, etc.) reveals several features that will **not** be present in the Python `debug_toolkit` by default. These are explicit architectural trade-offs made to achieve the 90% SLOC reduction:

1. **No Remote Web Access (WebSockets / Browser UI)**
   - *Legacy:* The Node backend fans out traffic via `GET /ws` to up to 100 concurrent clients. You could run the backend on a bench PC and connect from a phone or laptop.
   - *Toolkit:* CustomTkinter is a local desktop window. It cannot be accessed remotely via a browser.

2. **No REST API for Automation**
   - *Legacy:* Exposed endpoints like `POST /api/cmd/send` and `GET /api/can/frames` allowing external CI scripts or tools to orchestrate bench tests.
   - *Toolkit:* No HTTP server. Automated injection or testing must be done internally via Python scripts importing the `transport.py` module.

3. **No Playwright E2E UI Testing**
   - *Legacy:* The UI was tested via Playwright (`e2e/tests/debug-tool.spec.ts`) to ensure tabs, stores, and filters rendered correctly.
   - *Toolkit:* Desktop GUIs like Tkinter are notoriously difficult to E2E test. UI validation will be primarily manual, though the `decoder.py` and `sim_engine.py` will have unit tests.

4. **No SQLite Querying for Historical Data**
   - *Legacy:* Stored frames in a `can_frames` table, allowing complex SQL queries on historical recordings.
   - *Toolkit:* Uses in-memory `collections.deque` for live viewing and streams recordings directly to CSV/JSONL files. Advanced offline querying requires loading those files into Pandas or a separate database.

5. **No Native C++ IPC Models**
   - *Legacy:* Supported `modelBackend: "native"` to pipe simulation physics to native C++ binaries.
   - *Toolkit:* Relies purely on the Python implementation of the `EcuModel` interfaces (MtrModel, RtModel, etc.).
