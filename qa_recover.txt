
# QA Report: E-Trike RT Subsystem Analysis

## Overview
An architectural review and code audit was conducted on the `rt` (RT-ESP32 and RT-Aurix-Lite) project to evaluate the separation between prototype flags, safety-critical builds, traceability, hardware validation reports, and tested failure-mode evidence. Several severe issues were identified that must be addressed before any vehicle integration.

---

## 1. Safety-Critical Build Separation (SEVERE)
**Issue:** There is no separation between prototype/bench bypass flags and the safety-critical vehicle build.
**Details:** In both `rt-esp32/platformio.ini` and `sys-esp32/platformio.ini`, severe safety bypasses are directly embedded in the default `[env:esp32-s3-devkitc-1]` configuration. These include:
- `CONFIG_BENCH_SOLO` (Disables cross-ECU heartbeat timeouts)
- `CONFIG_BYPASS_EPS_C_SYNC` (Skips steering listen-sync)
- `CONFIG_BYPASS_SEB_SYNC` (Skips brake listen-sync)
- `CONFIG_BYPASS_MTR_ABSENT` (Skips EGAS L2 monitoring)

**The Problem:** The `architecture.md` document manually instructs developers to "Remove all `CONFIG_BENCH_*` and `CONFIG_BYPASS_*` before vehicle deployment." Relying on human intervention to manually comment out critical safety bypasses is an unacceptable risk for a safety-critical system. If the default build is accidentally flashed to a vehicle, the firmware will bypass fundamental safety mechanisms (heartbeat timeouts, steering/brake synchronization, and EGAS Level 2 monitoring), potentially leading to catastrophic failure.

**Action Required:** Implement strict build environment separation in the PlatformIO configurations (e.g., separating `[env:bench]` from `[env:vehicle]`). The default build target MUST strictly enforce all safety protocols without bypasses.

---

## 2. Lack of Tested Failure-Mode Evidence and Hardware Validation (SEVERE)
**Issue:** The project lacks documented evidence of hardware validation and tested failure modes.
**Details:** The `docs/hil-safety-test-plan.md` outlines 19 Hardware-in-the-Loop (HIL) safety tests covering critical failure modes such as ESTOP propagation, command staleness, steering following errors, dynamic angle clamps, and SEB comm-faults. However, the summary table shows every single test status as **"Not tested."**

**The Problem:** The system relies entirely on untested assumptions for critical safety features. For example, Test T1.2 (SEB Comm-Fault Behavior) is designed to determine if the brake holds or releases pressure upon CAN loss. Since this is untested, the assumption that a 20ms watchdog reset window mitigates brake loss (Gap #8) remains unvalidated. Without tested evidence, claims about EGAS L2 monitoring, follow-error timeouts, hold angles, and ESTOP ramp-to-zero are unverified.

**Action Required:** Halt any vehicle deployment until all 19 HIL safety tests are fully executed, validated, and documented. Produce a formal hardware validation report containing empirical failure-mode evidence.

---

## 3. Implementation and Traceability Gap in RT-Aurix-Lite (MAJOR)
**Issue:** Missing implementation and traceability for the consolidated Aurix architecture.
**Details:** The `rt-aurix-lite/rt-aurix-lite-architecture.md` file documents a consolidated architecture utilizing the AURIX TC3xx (combining RT and SYS capabilities). However, the `rt-aurix-lite` directory lacks any source code, build system, or integration testing setup.
**The Problem:** There is a severe traceability gap between the designed safety architecture and the actual codebase. Documenting a consolidated safety architecture without a corresponding traced implementation leads to a divergence in safety processes between the distributed ESP32 variant and the proposed AURIX TC3xx approach.

**Action Required:** Ensure that the architecture documents are synchronized with the actual codebase. If the Aurix variant is still in the conceptual phase, it must be explicitly marked as such, and safety-critical tracking should focus exclusively on the implemented ESP32 distributed variant.
